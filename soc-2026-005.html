SOC-2026-005: Successful SSH login minutes after a brute-force burst

A production incident investigation into an SSH brute-force burst, a successful root login five minutes later, and AppArmor denials one second after the login. The investigation established that the events were unrelated and there was no compromise.

01 / Executive summary

A brute-force burst against SSH (rule 5712, level 10) was followed five minutes later by a successful root login and, one second after it, six AppArmor denials. Read together, the sequence looked like an attacker had gained access and then encountered a system restriction.

The investigation established three separate facts: the brute force came from two internet scanners and failed; the login was the administrator's, using his own key and connection; and the AppArmor denials came from the who command run by Ubuntu's login banner.

Verdict: no compromise.

04 / Investigation

Three questions were answered with separate checks. Everything was read from the SIEM; nothing was run on production.

QuestionCheckResult
Who logged in at 18:07?full_log of rule 5715Root, administrator's public key, from a Senegalese IPv4 address
Is that IP the administrator's?curl -4 ifconfig.me from his machineSame IPv4. The first attempt returned IPv6, so the check was repeated with IPv4 forced to match the SSH connection.
Is it linked to the brute force?Source IPs of rule 5712Two different scanner IPs, neither matching the login source. Password authentication is disabled.
What did AppArmor block?full_log of rule 52002, parsed as JSONProcess and profile who; read of /etc/passwd and /etc/nsswitch.conf denied one second after login.

Why who runs at login: Ubuntu's login banner shows system information, including the number of logged-in users, which it gets from who. On Ubuntu 26.04, the command runs under an AppArmor profile that does not allow reading the user database. The read is denied, the command fails silently, and the banner shows less information.

This explanation was also observed on a second server on 23 November 2026: the Need Academy server, also running Ubuntu 26.04, showed "Users logged in: 0" during an active session.

An attacker's tool would not normally run as who within one second of an interactive login and touch only these two files. Combined with the verified key and IP, the explanation is consistent.

05 / Impact & response

Impact: none. The brute force failed, the login was legitimate, and the AppArmor denials only affected a line of the login banner.

Response actions: None required.

07 / Detection review
  • Built-in rules detected each step separately. Wazuh's correlation for failures followed by success only links events from the same source IP. A successful login from a different IP shortly after a brute force raises no combined alert; a human analyst must connect the events.
  • Rule 52002 (AppArmor denied, level 3) will repeat at every administrator login. It remains visible because AppArmor denials are rare and valuable on a production server.
08 / Lessons learned
  1. Alerts close in time are not necessarily related. Each relationship must be proven with evidence.
  2. A key fingerprint is stronger evidence than an IP address, which can change with the network.
  3. When checking an IP, match the protocol. The machine had both IPv4 and IPv6 addresses.
  4. Root logins make attribution harder. Named accounts would have answered "who?" directly.
